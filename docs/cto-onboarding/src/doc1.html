01한 장 요약

학생이 프로필을 한 번 등록하면, 흩어진 교내·교외 장학 공고를 자동으로 매칭받고 증명서류 준비와 공고 원본과 같은 구조의 신청서 작성까지 앱 안에서 끝낸다. 공고 데이터는 사람이 넣는 것이 아니라 매일 도는 수집 로봇이 41개 대학 게시판에서 가져온다. 서버는 사실상 없다 — 앱은 정적 파일이고, 데이터 파이프라인 전체가 GitHub Actions 위에서 돈다.

이 제품을 이해하는 열쇠 — "정직성"이 기능이 아니라 제약이다

창업자(이선주)와 합의된 8개 운영 원칙이 코드 구조를 지배한다. 핵심은 셋이다. ① 가짜 공지 금지: 실존하지 않는 장학금을 만들지 않는다. ② 추론 금지: 공고 원문에 적히지 않은 금액·자격·제출방법을 앱이 추측해 채우지 않는다(못 찾으면 "원문 확인"이라고 말한다). ③ 정직한 신청 상태: 실제 접수가 일어나지 않는 것을 "신청 완료"라고 쓰지 않는다.
→ 그래서 금액이 확정 표기된 공고가 188건 중 8건뿐이다. 이건 데이터 결함이 아니라 설계된 결과다. 이 원칙을 모르고 "빈 칸을 채우는" 개선을 하면 제품의 정체성이 깨진다.

02문제와 해법

사용자가 겪는 문제한대장이 하는 일구현 상태
공고가 학교 게시판·재단 홈페이지·한국장학재단에 흩어져 있다 41개 대학 게시판을 매일 2회 수집해 한 화면에 모은다 가동 피드 615건 + 큐레이션 188건
내가 지원 가능한지 공고를 다 읽어야 안다 프로필 1회 등록 → 12개 신호로 자격을 자동 진단하고 4단계로 판정 가동 적합도 점수 정렬
신청서 양식(HWP)을 받아 워드로 옮겨 적어야 한다 원본과 같은 구조의 문서를 앱이 생성 (.doc 저장·인쇄·공유) 가동 48종 · 공고 34건 연결
같은 증명서류를 매번 다시 뗀다 서류 보관함 8슬롯(기기 내 저장) → 신청 때 자동 체크리스트 가동
마감을 놓친다 마감 D-1·당일 푸시 알림(앱을 안 켜도 도착) 가동 Cloudflare Worker
최종 제출 버튼은 학교 전산에 있다 제출처 안내 + 내용 복사 + 이메일 접수 공고는 메일 자동완성 부분 진짜 원클릭은 5장 참조

›

03제품 헌법 — 운영 원칙 8개

전부 창업자와 합의된 것이고 변경 금지로 표기돼 있다. 코드 리뷰·기능 제안의 판단 기준이므로 CTO가 가장 먼저 알아야 할 목록이다.

#원칙코드에서의 강제 장치
1정직한 신청 상태진척도는 "신청 준비 완료"까지만 앱이 표기. 공식 제출·선정 결과는 사용자가 직접 기록(effectiveStep)
2등록은 컨펌 후 (자동 등록은 예외)보수적 규칙을 통과한 공고만 로봇이 자동 등록하고 앱에 '자동 등록·검수 전' 배지 표시. 킬스위치 auto-register-config.json
3선조치 후보고방향 결정이 필요하면 최적안으로 먼저 조치하고 무엇을 왜 했는지 보고
4양식의 정의공고 첨부 원본과 동일한 구조의 문서를 생성해야 한다. 자유서식 텍스트로 대체 금지. 증명 장치: verify/form-snapshot.mjs(48종 문자 단위 대조)
5양식 확보 절차정식 등록 시 첨부 신청서가 있으면 스키마화까지가 한 세트. 없으면 noForm:"사유" 기재 — 감사 통과 조건
6가짜 공지 금지임의 생성 공고 0건. 실존 상시 제도(국가장학금 등)는 임의 마감일 없이 '상시 제도'로 표기
7소급 적용엔진·정책이 바뀌면 신규가 아니라 전수에 적용. 강제 장치: verify/audit-data.js(실패 시 그날 수집 결과를 저장하지 않음)
8-1추론 금지 · 원문 발췌신청방법·제출서류는 확보한 공고 전문에서 원문 문장을 그대로 발췌해서만 표시. 발췌 없으면 '원문 보기' 링크만
8-2앱 제작 문서 한정앱이 만든 지원문서는 자유형식 제출이 원문으로 확인된 공고(prepDoc:true)에만 제공
