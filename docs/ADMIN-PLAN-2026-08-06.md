## Context (왜 하는가)

관리자 화면(`_admin/`)은 14차 세션에서 1단계로 만들어졌고, 아직 Cloudflare에 올라가 있지 않다.
올리기 전에 개발자(선주)가 **기능 추가와 인터페이스 개선**을 지시했다.

조사 결과 지금 화면은 **읽기는 넓고 쓰기는 좁다.** 특히 코드에 그대로 적혀 있듯
(`_admin/admin.js:569-570`, `:599`) **"등록 버튼은 다음 단계에 붙습니다"** — 수집된 공고 608건 중
**등록 후보 268건**이 쌓여 있는데 화면은 보여만 주고 등록할 방법이 없다. 관리자 화면을 만든
목적("학생인 척 접속하지 않고 공고를 보고 고치고 컨펌한다")의 절반이 비어 있는 상태다.

## B단계 — 인터페이스 정비

> **개발자 피드백(2026-08-06)**: "가독성이 떨어지고 조작이 어렵다"는 지적이 여러 차례 있었다.
> 아래 **B0**이 그 대응이고, 나머지보다 먼저 한다. 예쁘게 만드는 일이 아니라 **읽고 누르는
> 도구로서의 기본 치수를 다시 잡는 일**이다.

### B0. 읽고 조작하는 기본 치수 다시 잡기 ← 최우선

**진단 (실측)**

| 요소 | 지금 | 문제 |
|---|---|---|
| `.row .t` 공고 제목 (`admin.css:237`) | `.92rem` ≈ **13.8px** | 목록에서 가장 중요한 글자가 본문(15px)보다 작다 |
| `.row .m` 학교·기관·채널 (`:238`) | `.79rem` ≈ **11.9px** + `--ink-3` | 한글 11.9px는 뭉갠다 |
| `.pill` 상태 배지 (`:246`) | `.7rem` ≈ **10.5px** | 상태가 가장 안 보인다 |
| `th` 표 머리글 (`:260`) | `.72rem` ≈ 10.8px + `text-transform:uppercase` | **한글에 uppercase는 효과가 없고 자간만 벌어져** 읽기만 나빠진다 |
| `table` (`:258`) / `.card .d` (`:197`) | `.86rem` / `.82rem` | 12.9px / 12.3px |
| `.card .v` 숫자 (`:193`) | `1.75rem` = 28px | 제목의 2배 — **눈이 숫자에만 간다** |

**대비 실측** — `--ink-3`(#7b8194) on `--paper`(#fbfaf8) = **3.72:1**.
작은 글자 기준 4.5:1 미달(큰 글자 기준 3:1은 통과). 하필 가장 작은 `.row .m`이 이 조합이다.
`--ink-2`(#4c5262)는 **7.58:1**로 통과. 다크 모드의 같은 색은 #13151c 위에서 **5.05:1**로 통과 —
**밝은 화면에서만 미달**이다(낮에 유독 안 보이는 이유).

**조치**

1. **타이포 치수 재설정** — 본문 15 → 16px 기준으로:
   공고 제목 `1rem`/650 · 메타 `.875rem`(14px) · pill `.78rem` · 표 `.9rem` · 표 머리글 `.8rem`.
   `th`의 `text-transform:uppercase`와 `letter-spacing`은 **삭제**(한글 전용 화면이다).
2. **색 규칙 한 줄로 못 박기** — `--ink-3`는 **14px 이상에만** 쓴다. 그 아래는 `--ink-2`.
   `.row .m`·`.card .d`·`.empty`가 해당된다. 다크 모드 조합도 함께 확인.
3. **터치 목표 최소 40px** — `.chip`(`:210`, 지금 약 26px)·`.btn-sm`(`:171`)·`.tab`에 `min-height`.
   손가락으로 필터를 고를 수 있게 된다.
4. **누를 수 있다는 표시** — `.row` 오른쪽에 `›`, `:active` 배경(모바일엔 `:hover`가 없다),
   `cursor:pointer`만으로는 부족하다. (B6의 `role="button"`과 한 세트)
5. **목록 한 줄 다시 설계** (`rowHtml` `admin.js:459`) —
   제목 / 메타를 `·`로 구분해 **정해진 순서**(학교 · 기관 · 접수)로,
   배지를 **종류별 색**으로(지금은 전부 `pill bad` 빨강이라 무엇이 문제인지 구분이 안 된다),
   모바일에서도 제목 우측에 D-day 고정.
6. **스캔 지점 만들기** — 구분선(`--rule-soft`, 거의 안 보임)을 한 단계 진하게 + 목록을
   **마감 임박 / 이번 주 / 기한 미확인** 구획으로 나누거나 학교별 sticky 머리글.
   161줄이 똑같은 높이·색으로 이어져 눈이 멈출 자리가 없다.
7. **밀도 토글** (편안하게 / 촘촘하게) — 훑을 때와 검수할 때 필요한 밀도가 다르다.
8. **'오늘 할 일' 우선순위화** (`renderTodo` `:415`) — 카드 9장이 **전부 동급**이라
   급한 것과 참고가 구별되지 않고, **0건인 초록 카드가 첫 화면의 2/3를 먹는다.**
   → 할 일이 있는 카드만 크게 위로, 0건은 **"정상 5항목 ✓" 한 줄 띠**로 접는다.
9. **필터 접기** (`renderList` `:526`) — 지금 **5줄**(상태·소속/성격·접수·경고등·검색)이 항상
   펼쳐져 목록을 화면 밖으로 밀어낸다. → 기본은 **상태 칩 + 검색 한 줄**, 나머지는 '필터 더보기'.
   적용된 필터는 목록 위에 **지울 수 있는 태그**로 표시. 모바일은 하단 시트.
10. **표를 좁은 화면에서 카드형으로** — 지금은 `.scroller`의 가로 스크롤인데 발견성이 나쁘다.
11. **시트 하단 고정 동작 바** — 저장/컨펌/닫기가 스크롤에 묻힌다(닫기는 우상단 하나뿐).
12. **색만으로 뜻을 전하지 않기** — `.dd.near`(빨강)/`.dd.soon`(노랑)이 모양이 같다. 기호를 더한다.

**확인 방법**: 구현 중 `playwright-core`를 설치해 **고치기 전후 스크린샷을 찍어 비교**한다
(이 샌드박스에 playwright가 없어 이번 조사에서는 코드로만 판단했다). 개발자에게는
`node tools/build-admin-preview.mjs`로 만든 미리보기 파일을 보내 실제 폰에서 확인받는다.

### B1. 잘려 나간 데이터를 볼 수 있게
하드 잘림 4곳에 "N건 더 보기" 버튼(기본 50건씩):
`admin.js:601`(미등록 후보 80) · `:607`(제외분 60) · `:855`(죽은 링크 60/전체 256) · `:868`(이력 100).
지금은 268건 중 80건, 256건 중 60건만 화면에서 도달 가능하다.

### B2. 정렬
표 헤더를 누르면 정렬(마감 / 상태 / 학교 / 제목 / 실패 횟수). 상태는 필터 객체 `F`(`admin.js:480`)에
`sort`·`dir` 키를 더해 함께 보관. 지금은 **어디에도 사용자 정렬이 없다.**

### B3. 다중 선택 + 일괄 처리 ← 체감이 가장 큰 항목
`rowHtml`(`:459`)에 체크박스, 화면 하단에 선택 바(선택 N건 · 컨펌 · 삭제 · 되돌리기).
**저장소 쪽은 고칠 필요가 없다** — `tools/admin-apply.mjs`의 `confirm`/`revert`/`remove`가 이미
`payload.ids` 배열을 받아 순회한다(`:51`). 화면이 배열을 안 보내고 있을 뿐이다.
기존 `#btn-confirm-clean`(`:1145`)은 "몇 건"만 알려 주고 무엇인지 안 보여 주므로, 선택 결과를
**목록으로 펼쳐 보여 준 뒤** 확인받는 방식으로 교체.

### B4. 행에서 바로 하는 동작
검수 전 행 우측에 '컨펌' 버튼. 지금은 무슨 일이든 시트를 열었다 닫아야 한다.

### B5. 되돌릴 수 없는 동작의 확인 절차
`window.confirm` 6곳(`:1105, 1141, 1150, 1196, 1200, 1221`) → 시트 안 확인 화면으로.
**대상 목록을 실제로 보여 준 뒤** 확인받는다(삭제·합치기는 git 말고는 되돌릴 방법이 없으므로).

### B6. 키보드·읽어 주기
- 목록 행·양식 행에 `tabindex="0" role="button"` + Enter/Space (지금은 **마우스로만** 상세를 열 수 있다)

### B7. 다시 그릴 때 잃는 것

## C단계 — 등록 파이프라인 (가장 큰 구멍)

### C1. 저장소 쪽: `register` 동작 신설
`tools/admin-apply.mjs`의 `switch`(`:56`)에 `case 'register'` 추가.

- 입력: `{ notice: {url, title, school}, patch: {...} }`
- **id 생성·중복 판정은 `collector/auto-register.mjs`와 같은 규칙을 써야 한다.** 규칙이 갈라지면
  로봇이 같은 공고를 다시 등록한다. 공용으로 뽑아 쓰거나 그 파일의 함수를 import.
- **`verify/entry-rules.cjs`의 `checkEntry`를 등록 전에 통과시킨다** — 로봇이 쓰는 그 규칙이다.
  대출·대학원 전용·행사·목록 주소 등이 사람 손으로도 안 들어간다.
- `sourceKind: 'admin'`, `listedAt` 자동, `auto`는 넣지 않는다(사람이 등록 = 검수 완료 상태).
- 워크플로 `git add`(`admin-apply.yml:81-82`)는 `data/registered.json`을 이미 담고 있어 **변경 불필요**.

### C2. 화면 쪽
컨펌 작업대의 미등록 목록(`unregHtml()` `:571`) 각 행에 **'등록하기'** 버튼 →
등록 시트가 열린다. 구성은 기존 `detailSheet`(`:906`)의 두 칸 대조를 그대로 재사용:

- **왼쪽** = 채울 칸(제목·주관·구분·금액·마감·기간·요약·주소·학교 한정)
  — 수집된 공고에서 아는 것(제목·주소·학교)은 미리 채워 둔다
- **오른쪽** = 공고 원문 발췌 + 첨부 (지어내지 말라는 안내 문구 그대로)

`_admin/README.md`의 '화면 여섯 개' 표와 `admin.js:599`의 "등록 버튼은 다음 단계에 붙습니다"
문구도 함께 고친다.

## 순서 권고

**0 → A → B0 → B3·B1 → C → E → D → 나머지 B**

- **A(신뢰성)를 맨 앞에** — 화면을 믿을 수 있어야 나머지 판단이 의미가 있다.
- **B0(치수·대비)를 그다음에** — 개발자가 직접 겪은 문제이고, `admin.css` 위주라 **데이터를

  **먼저 잡아야 두 번 일하지 않는다.**
- **B3(다중 선택)를 C보다 먼저** — **저장소 쪽 변경이 전혀 필요 없어**(`admin-apply.mjs`가 이미

- C(등록)·E(로봇)·D(자격/양식)는 각각 저장소 쪽 쓰기 경로를 새로 만들어야 해서 뒤에 둔다.
