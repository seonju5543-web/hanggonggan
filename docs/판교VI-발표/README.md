## (완료된 지시) 발표 대본 작성

**발표자료(PPT)는 2026-08-11에 완성됐다. 남은 작업은 대본 하나다.**

## ⚠️ 먼저 알아야 할 것 — 실제 발표자료는 이 폴더의 구성안과 다르다

**개발자가 외부 플랫폼에서 직접 만든 PPT가 실제 발표자료다.**
이 폴더의 `02_슬라이드구성.md`는 제작 과정에서 세운 **설계안**이며, 최종 덱과 장수·순서·문구가
다를 수 있다. `build_deck.js`와 `90_부록`도 채택되지 않은 참고본이다.

**대본은 반드시 개발자가 제시하는 실제 PPT를 기준으로 쓴다.**
이 폴더의 문서는 **맥락·사실·전략**을 주는 자료이지, 덱의 정본이 아니다.

| 이 폴더에서 그대로 쓸 것 | 실제 PPT에 맞춰 조정할 것 |
|---|---|
| `01_현황블록.md` 숫자·기능 (실측 검증본) | 슬라이드 장수·순서 |
| `03` 대본 톤·금지사항 | 슬라이드별 시간 배분 |
| `04` 예상 질의응답 | 백업 슬라이드 번호 |
| `05` 대표 문장 | 캡쳐 배치 |

## 세션을 열자마자 할 것

### 1. 개발자에게 완성된 PPT를 요청한다
```
완성하신 발표 PPT 파일을 올려주세요. 슬라이드 순서와 실제 문구를 보고 대본을 씁니다.
```
**PPT는 이 저장소에 없다.** 개발자가 외부 플랫폼에서 만들어 로컬에 갖고 있으므로 반드시 받아야 한다.
받기 전에 대본을 쓰면 슬라이드에 없는 내용을 말하게 되어 못 쓴다.

### 1-1. 받은 PPT를 먼저 읽고 이 폴더와 대조한다
- 실제 장수와 순서를 파악한다
- `01_현황블록.md`의 숫자와 **다른 수치가 슬라이드에 있으면 개발자에게 확인**한다
  (서면 사업계획서와 어긋나면 감점이므로 그냥 넘기지 않는다)
- `04_예상질의응답.md`의 백업 슬라이드 번호를 실제 덱 번호로 다시 매긴다

### 2. `03_대본작업_지침.md`를 읽고 그대로 작업한다
대본에 무엇이 들어가야 하는지, 어떤 톤으로 써야 하는지가 전부 정리돼 있다.

### 3. 산출물
- 슬라이드별 발화 스크립트 (실제로 읽을 문장)
- 7분 시간 배분 (슬라이드별 초 단위)
- **예상 질의응답 8분치** — `04_예상질의응답.md`가 초안이며 여기서 확장한다

## 왜 대본이 특히 중요한가

이 덱은 **키워드형**이다. 개발자 지시로 슬라이드에서 서술문을 전부 걷어냈다.
그래서 **슬라이드가 알려주지 않는 것을 발표자가 전부 말로 채워야 한다.**
대본 없이 들어가면 여백에서 말이 막힌다.

그리고 **질의응답이 8분으로 발표(7분)보다 길다.** 질문을 막는 것이 아니라
**내가 답할 수 있는 질문이 나오게 만드는 것**이 이 발표의 실제 승부처다.
덱에는 이미 그 미끼가 심어져 있다 (`04_예상질의응답.md` 참조).

## 이 폴더가 존재하는 이유

2026-08-12 경희대 창업보육센터(판교VI캠퍼스) **입주 발표평가**용 자료 작업이다.
서면 사업계획서는 2026-08-09 제출·1차 서류 통과, 발표평가 전날(8/11)에 발표자료를 준비했다.

앱 코드와 무관한 대외 자료지만 **한대장 자체를 설명하는 문서**이고 다음 세션이 이어받아야 하므로
저장소에 남긴다.

**개인정보는 이 폴더에 넣지 않는다.** 제출한 신청서에는 대표자 생년월일·연락처·이메일이 있으나
전부 제외했다. **이 저장소는 공개(public)이므로 앞으로도 넣지 말 것.**

## 발표 조건 (대본을 쓸 때의 전제)

- **7분 발표 + 8분 질의응답**
- 심사위원: **대학 교수·산학협력단 심사역.** 전문성이 매우 높다
- 심사위원은 **서면 사업계획서를 이미 읽은 상태**
  → 덱과 대본은 요약이 아니라 **"이미 만들어 놓고 돌리고 있다"의 증명**이다
- 발표자: 조세현(대표, 경희대 재학) — 대면 PT

---

## 절대 규칙 (대본에도 그대로 적용)

1. **숫자를 바꾸지 않는다.** 서면과 어긋나면 그 자체로 감점. 반올림·근사 금지
2. **경쟁사를 실명으로 말하지 않는다.**
   → **중요: 서면 사업계획서 p.6의 경쟁사는 실재하지 않는 회사다**(개발자 확인).
   심사위원이 물으면 회사가 아니라 **도달 지점(조회 vs 신청 완결)**이라는 축으로 답을 돌리고,
   **"저희가 확인한 범위에서는"**이라는 단서를 반드시 붙인다
3. **미완성 항목을 성과로 말하지 않는다.** 접수 메일 서버(발송 키 대기) 등은 물어보면 답하되
   먼저 꺼내지 않는다
4. **과장 금지.** "혁신적", "최고의", "게임체인저" 같은 표현을 대본에 쓰지 않는다

### 코드 대조로 잡은 정정 5가지 (대본에서도 지킬 것)
1. **적합도는 실제 5~99%** — `Math.max(5, Math.min(99, score))`. 코드 주석의 0~99는 부정확
2. **관리자 탭은 7개** — 오늘 할 일 / 공고 전체 / 컨펌 작업대 / 양식 / 수집망 / **로봇** / 데이터 품질
3. **앱 하단 탭 4개** — 홈 / 장학금 / 신청내역 / MY
4. **알림 5종 구현됨** — 새 공고 / 마감 하루 전·당일 / 제출 리마인드 / 결과 기록 리마인드 / 우리 학교 새 공고
   → 2번 슬라이드 "마감 놓치면 소득 손실"을 정확히 겨냥. **대본에서 이 연결을 반드시 말할 것**
5. **제출 버튼 실물 4종** — 내용 복사하고 제출처 열기 / 서류 내용 복사 / 파일과 함께 공유 / 접수 메일 열기
