# 한대장 회원 서버(Supabase) 구조 설명서

> 2026-10-10 · 유은서(CTO) · 팀 업무 분장 백엔드 4번
> 대상: 코드를 몰라도 "회원 정보가 어디에 어떻게 저장되는지" 알아야 하는 팀원 전부.
> 원본은 `supabase/migrations/` 의 파일 4개다. 이 문서가 그 파일과 다르면 **파일이 맞다.**

## 1. 한 줄 요약

Supabase는 **회원 장부를 대신 보관해 주는 회사**다. 우리 앱은 장부에 표 4개를 두고 쓴다.
로그인하지 않은 학생은 이 장부를 전혀 쓰지 않는다. 그 학생의 정보는 전부 휴대폰 안에만 있다.

```
학생 휴대폰 ──(로그인한 경우에만)──▶ Supabase 서울 서버
   │                                   ├─ 회원 명단(auth.users)      ← Supabase가 관리
   │                                   ├─ ① profiles       프로필·신청내역
   │                                   ├─ ② login_events   로그인 기록
   │                                   ├─ ③ apply_sends    대신 보낸 지원 메일 기록
   │                                   └─ (④는 ①에 칸을 더한 것)
   └─ 서류 사진·주민번호·계좌번호·자기소개서는 여기에 **안 간다** (휴대폰에만)
```

- 주소: `https://ffnzmiorcojbhpqwqgcy.supabase.co` (앱의 `supabase-config.js`)
- 공개 열쇠(`sb_publishable_…`)는 원래 공개되는 값이다. 숨길 필요가 없다.
- **비밀 열쇠(`service_role`)는 저장소·채팅에 절대 넣지 않는다.** 서버(Cloudflare Worker)의 비밀 칸에만 둔다.

## 2. 회원 명단 (auth.users) — Supabase가 알아서 관리

이메일, 비밀번호(암호화된 형태), 가입일이 들어 있다. 우리가 직접 만든 표가 아니다.
비밀번호 암호화, 메일 인증, 비밀번호 재설정, 구글·카카오 로그인은 Supabase가 처리한다.
아래 표 3개는 모두 이 명단의 **회원 번호(user_id)** 로 이어진다.
**회원이 탈퇴하면 그 회원의 줄이 표 3개에서 자동으로 함께 지워진다**(on delete cascade).

## 3. 표 ① profiles — 프로필과 신청내역 (회원 1명 = 1줄)

| 칸 | 무엇 | 예 |
|---|---|---|
| user_id | 회원 번호 | (자동) |
| profile | 프로필 전체를 **한 덩어리**로 | 학교·학과·학년·성적·소득구간·특별자격 |
| applications | 신청내역 목록 | 어느 공고를 언제, 어디까지 했는지 |
| sensitive_ok | 민감정보(장애·기초수급·국가유공자) 보내기에 동의했는지 | true/false |
| updated_at | 마지막으로 고친 시각 | 2026-10-10 14:03 |
| school, major, grade, gpa, income_bracket … (11칸) | profile 덩어리에서 **자동으로 꺼낸** 칸 | 한국외국어대학교 / 3 / 3.5 |

**왜 한 덩어리로 넣었나**: 앱의 프로필 모양은 이미 두 번 바뀌었다. 칸을 잘게 나눠 두면
앱을 고칠 때마다 장부 설계도 같이 고쳐야 하고, 깜빡하면 값이 조용히 사라진다.

**그럼 11칸은 왜 또 있나**(0004 파일): 통계를 내거나 서버가 자격을 다시 확인할 때 덩어리를
매번 뜯으면 불편하다. 그래서 **장부가 덩어리에서 직접 꺼내 채우게** 했다. 앱이 따로 써 넣는
길이 없으니 두 곳이 어긋날 수 없다. 꺼낸 칸에는 **검문**도 걸려 있다.
성적 0~4.5, 학년 1~8, 소득구간 1~10 밖의 값이 들어오면 저장 자체가 거절된다.

**서버로 안 가는 것** (앱의 `supabase-client.js` → `syncSafeProfile`, `syncSafeApplications`가 떼어 낸다):
주민등록번호 · 계좌번호 · 신청서에 쓴 답(`formAns`) · 첨부 서류 · 동의하지 않은 민감정보.
→ 이 약속은 `terms.html` 개인정보처리방침에 그대로 적혀 있다. 코드와 약관이 어긋나면 법적 문제가 되므로
**한쪽을 고치면 다른 쪽도 같이 고친다.** 검사: `verify/verify-supabase.js`(가짜 서버로 나가는 내용을 전부 세어 본다).

**두 기기가 동시에 고치면?** 앱은 "내가 마지막으로 본 시각"을 기억해 두고, 서버가 그 뒤로
바뀌지 않았을 때만 덮어쓴다. 바뀌었으면 덮지 않고 둘을 합친다(`app.js syncApplyRemote`).
예전에는 B폰이 A폰의 신청서를 지우는 사고가 실제로 재현됐다.

## 4. 표 ② login_events — 로그인 기록 (로그인할 때마다 1줄)

| 칸 | 무엇 |
|---|---|
| at | 로그인한 시각 |
| device | 대략적인 기기 이름 ("아이폰 · Safari") |
| client | 이 설치본을 가리키는 뜻 없는 난수 ('현재 기기' 표시용) |

IP 주소와 위치는 **담지 않는다.** 학생은 MY → 설정 → 로그인 활동에서 이 기록을 본다.
**기록은 고칠 수 없다**(넣기·읽기·지우기만 가능). 고칠 수 있으면 침입자가 흔적을 지울 수 있다.

## 5. 표 ③ apply_sends — 앱이 대신 보낸 지원 메일 기록

"냈다/못 받았다" 분쟁을 가리려는 **증빙**이다.

| 칸 | 무엇 |
|---|---|
| notice_id | 어느 공고 |
| to_email | 어디로 보냈나 (공고에서 읽은 주소) |
| subject | 메일 제목 (본문은 안 담는다) |
| status | 보냄 → 도착 / 반송 / 스팸신고 / 실패 |
| detail | 실패 사유 (메일 회사가 준 문구 그대로) |

학생은 **읽기만** 할 수 있다. 쓰는 것은 서버만 비밀 열쇠로 한다. 학생이 증빙을 조작할 수 없게 하려는 것이다.

## 6. 진짜 보안 장치 — "자기 줄만" 규칙 (RLS)

공개 열쇠는 누구나 볼 수 있다. 그래서 남의 정보를 못 보게 막는 것은 **표마다 걸린 규칙 하나**뿐이다.

| 표 | 읽기 | 넣기 | 고치기 | 지우기 |
|---|---|---|---|---|
| profiles | 자기 것 | 자기 것 | 자기 것 | 자기 것 |
| login_events | 자기 것 | 자기 것 | **아무도 못 함** | 자기 것 |
| apply_sends | 자기 것 | 서버만 | 서버만 | 서버만 |

🔴 **이 규칙(Row Level Security)을 대시보드에서 끄면 전 회원 정보가 열린다.** 표를 새로 만들 때도
반드시 켜고 규칙을 적는다.

## 7. 표를 바꾸는 방법 (절차)

1. 대시보드에서 **손으로 고치지 않는다.** 언제 왜 바꿨는지가 남지 않는다.
2. `supabase/migrations/0005_무엇.sql` 처럼 **다음 번호로 새 파일**을 만들고, 맨 위에 이유를 적는다.
3. 그 파일을 대시보드 → SQL Editor에 붙여 넣고 실행한다. (Supabase는 저장소를 보고 자동 반영하지 않는다.)
4. 담는 정보가 늘면 `terms.html`의 수집 항목 표도 **같은 커밋에서** 고친다.

## 8. 알아 둘 운영 사실

- 무료 등급은 **7일 동안 아무도 안 쓰면 프로젝트가 일시정지**된다(대시보드에서 다시 켬). 사용자가 늘면 걱정 없다.
- 데이터 위치는 서울(Northeast Asia). 그래도 회사가 해외 법인이라 개인정보처리방침에 **국외 이전 고지**를 해 두었다.
- 앞으로 계획(BUSINESS.md): 프로필을 모아 B2B 맞춤 광고 근거로 쓴다. 이때도 위 "안 가는 것" 목록은 그대로다.
