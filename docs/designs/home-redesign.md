# 홈 화면 전면 교체 — 조사와 후보 3안 (2026-09-19)

> 개발자 지시: *"홈화면 디자인을 전면 교체하고 싶은데 UI bowl 커넥터를 통해 타 앱들의 사례를 보고
> 어떤 식으로 홈화면을 꾸미면 좋을지 후보를 추려줘. 디자인 측면의 모두를 개선시키고 싶어.
> 버튼, UX, 기능 탭 추가, 기능 탭 디자인 등의 부분에서"*
>
> 🔴 **아직 앱 코드는 한 줄도 안 고쳤다.** 이 문서와 시안 한 장이 전부다 —
> 개발자가 번호를 고르면 그때 만든다. 시안: `docs/designs/mockups/home-redesign.html`

## 1. 왜 시안부터 만들었나

개발자는 코드를 읽지 않는다. 글로만 된 후보는 고를 수 없어서, **눈으로 보고 번호로 고를 수 있는
한 장**을 먼저 만들었다(`design-conflicts.html` 과 같은 방식). 그 안의 숫자는 전부 **브라우저로 직접 재서**
넣었다 — 이 저장소가 반복해 겪은 사고가 '코드만 읽고 화면을 단정하는 것'이라(「매 세션 이것만은」 1·5번),
이번엔 앱을 띄우고 홈을 찍어 놓고 셌다.

## 2. 실측 — 지금 홈에서 실제로 일어나는 일

프로필: 한국외대 서울캠퍼스 3학년 경영 · 화면 390×844 · 2026-09-19 기준.

### 2-1. 홈 길이의 74%가 학교 게시판 링크다

| 구역 | 높이 | 비율 |
|---|---|---|
| 우리 학교 게시판 글 18건 | 2,583px | **74%** |
| 나에게 맞는 장학금 (3장 펴짐) | 359px | 10% |
| 금액 히어로 | 206px | 6% |
| 헤더·여백·기타 | 326px | 10% |
| **홈 전체** | **3,474px** | |

게시판 카드는 **우리가 원문을 읽은 적이 없어 주최도 모르는** 글이다(제목·링크뿐 — 2026-09-18 개발자 지시로
'교내' 칸에서 홈으로 옮겨 온 그 카드들이다). 즉 학생이 홈에서 스크롤하는 것의 대부분은
**앱이 아무것도 판단해 주지 못한 외부 링크**이고, 앱이 판단한 목록은 10%다.

### 2-2. 적합도 숫자가 앱을 스스로 깎아내리고 있다

홈에 올라올 수 있는 공고 **89건** 전수:

| 잰 것 | 값 |
|---|---|
| 자격 **미달**(`fails` 있음) | **0건** |
| 적합도 **40% 미만**으로 뜨는 것 | **84건** |
| 적합도 **60% 이상** | **0건** |
| 판정이 `unknown` | 85건 (나머지 4건은 `selective` · **`eligible` 0건**) |

첫 카드의 `적합도 50%` 를 열면 속은 `met 1 · total 2 · unknown 1 · fails []` 다 —
**아는 조건 2개 중 1개는 맞았고 1개는 우리가 모르며, 안 맞는 건 하나도 없다.**
그걸 "50%"로 적으면 학생은 *반만 자격이 된다* 고 읽는다. 지금 첫 화면 석 장이 전부 이 상태다(50·50·33%).

🔴 이 값은 `m.fit`(숫자)과 `m.fd`(`{pct,met,total,unknown,fails}`)에서 온다. **퍼센트로 판단하지 말 것** —
CLAUDE.md 「상수의 뜻」 절이 이미 같은 경고를 하고 있다.

### 2-3. 홈 공고의 93%는 '재단이 적어 둔 칸'이라, 시킬 수 있는 일이 '원문 확인'뿐이다

89건 중 **층2(KOSAF) 83건 / 층1 6건**, 상위 10장 중 9장이 층2.
**신청서 양식(`formId`)이 붙은 공고는 89건 중 1건**, 앱이 지원문서를 만들어 주는 공고(`prepDoc`)는 **0건**.

→ 그래서 홈의 주 버튼을 **"서류 담기 / 신청 준비"로 두면 대부분의 공고에서 할 일이 없다.**
지금 데이터로 정직한 주 동작은 **"공고 원문 열기"** 다. 시안 A·C의 첫 판이 '서류 2개만 더 담으면 돼요'였는데
실측에서 성립하지 않아 고쳤다 — **없는 기능을 그린 그림은 시안이 아니라 거짓말이다.**

### 2-4. 그 밖에 눈으로 본 것

- 첫 화면의 가장 큰 덩어리(`최대 400만원`)는 4건을 **전부** 받았을 때의 숫자라 할 일을 말하지 않는다.
- 지름길이 없다 — 달력은 신청내역 안, 서류함은 MY 안, 도우미는 떠다니는 동그라미.
- 실측 당시 **오늘 마감(D-DAY)** 인 공고가 카드 석 장 중 맨 아래에서 접힘선에 잘려 있었다.
- 도우미 마스코트의 '끌어서 이동 가능' 말풍선이 셋째 카드 금액 줄을 덮고 있었다.
- 게시판 카드의 파란 머리글이 화면에서 채도가 가장 높다 — **확인 안 된 정보가 확인된 정보보다 눈에 먼저 띈다.**

## 3. 후보 셋 (시안 참조)

| | A · 오늘 할 일 | B · 한눈에 보는 판 | C · 오늘의 한 건 |
|---|---|---|---|
| 첫 화면이 하는 말 | "이걸 하세요" | "당신 상태는 이렇습니다" | "이거 하나 보세요" |
| 게시판 74% 문제 | 3건만 남기고 접음 | 3건만 남기고 접음 | **갈래로 접어 기본 0건** |
| 기능 탭 | 4탭 그대로 | **달력 탭 신설(5탭)** | 가운데 동작 버튼 |
| 드는 일 | 작다 | 중간 | 중간 |
| 판단 | **먼저 이것** | 달력만 떼어 A와 같이 | A가 자리 잡은 뒤 |

셋은 배타적이지 않다. 제일 나은 조합은 **A의 할 일 카드 + A의 지름길 4칸 + B의 달력 탭 + C의 게시판 갈래**.

근거로 본 타 앱(UI bowl): 토스(홈 맨 위 '할 일' 카드) · 신한 슈퍼SOL(섹션 카드를 쌓은 '쉬운 홈') ·
원티드(제목 아래 아이콘 4칸 + 가로 스크롤 추천) · 플랭/말해보카(오늘 할 것 한 장 + 큰 버튼) ·
채비(하단 가운데 동그란 주 동작) · 젠디(한 화면 안에서 갈래를 가르는 알약 탭) · 무디(달력을 요약 카드로 접기).

## 4. 기능 탭 — 실측이 말하는 것

- **달력 탭 신설**을 추천한다. 이미 만들어 둔 달력(`verify/verify-calendar.js` 32항목이 지키는)이
  신청내역 화면 **안쪽**에 있어 학생이 있는 줄 모른다. 마감으로 먹고사는 앱에서 달력은 한 번에 닿아야 한다.
- **가운데 '신청 준비' 동그란 버튼은 아직 이르다** — 양식 1건·prepDoc 0건이라 눌러도 별일이 없는 자리가 된다.
  양식이 늘면 그때 얹는다.
- **탭은 다섯을 넘기지 않는다.** UI bowl 에서 본 사례(신한·토스·빼기·채비·보맵)가 전부 5가 한계였다.
- 게시판은 탭을 늘리지 않고 **홈 안 갈래(알약 탭)** 로 접는 것이 가장 싸다.

## 5. 어느 안을 고르든 같이 할 손질 여섯

1. **적합도 숫자 → 말로** (`미달 조건 없음` / `조건 확인 필요`). 판정은 `app.js` 의 `fitVerdict` 를 **그대로 쓴다** —
   규칙을 한 벌 더 만들면 화면과 알림이 갈라진다(이 저장소가 반복해 겪은 사고).
2. **확인한 것과 아닌 것의 위계 뒤집기** — 원문을 읽은 공고가 면(흰 카드), 게시판 링크는 회색 글씨 줄.
3. **주 버튼 높이 통일** 48px · 모서리 13px · 누르면 0.95(2026-09-11 개발자가 정한 값).
4. **비활성 버튼의 말** — `준비할 장학금이 남아 있지 않아요` 를 버튼 밖 한 줄로 내린다.
5. **마스코트를 비킨다** — 내려갈 때 접히고 멈추면 편다(`interactions.js` 에 얹는다).
6. **빈 화면에 다음 행동을 준다** — 프로필 채우기 · 조건 다시 보기.

## 6. 만들 때 주의 (되돌리면 깨진다)

- 🔴 **판정을 새로 만들지 않는다** — 적합도·마감·교내외는 각각 `fitVerdict` · `dday()` · `noticeKind` 한 곳뿐이다.
- 🔴 **`#home-deadline-list` · `#home-deadline-more` 표식을 바꾸지 말 것** — style.css 규칙과 검사 드라이버가 이 이름에 붙어 있다.
- 🔴 **'몇 장 펴는가'는 `HOME_DEADLINE_TOP` 하나가 정한다** — CSS 에 숫자를 두면 둘이 갈라진다(2026-09-12 코드 리뷰가 잡은 것).
- 🔴 **탭을 늘리면 `verify/` 드라이버가 같이 죽는다** — 화면을 옮길 때 검사 드라이버도 같이 옮긴다(2026-09-11 사고).
- 🔴 히어로를 걷어낼 때 **금액 회계는 `sumAmounts` 그대로** — 어림잡기(`estimate:true`)를 켜는 곳은 `renderHome` 하나다.
- ⚠️ 홈에 신청 현황을 **다시 만들지 말 것** — 2026-09-12 지시로 신청내역으로 옮긴 것이다(사본이 둘이면 갈라진다).

## 7. 실측을 다시 하려면

앱을 띄우고(`python3 -m http.server <포트>`) Playwright 로 홈을 연 뒤, 프로필을 `localStorage` 에 심고
`dismissNotify(page)`(`verify/onboard-helper.js`)로 알림 시트를 치운 다음 잰다.
🔴 **포트를 8123으로 쓰지 말 것** — 다른 워크트리 서버일 수 있다(`assertOwnServer` 가 막아 준다).
브라우저는 `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`, 모듈은 전역 `playwright` 다
(`playwright-core` 는 이 저장소에 설치돼 있지 않다).
색 토큰은 **파일을 읽지 말고 `getComputedStyle(document.documentElement)` 로 읽는다** —
`style.css` 는 `:root` 를 열 벌 겹쳐 써서 앞 블록만 읽으면 정반대로 읽는다(앞은 '놋쇠', 실효는 **남색 `#1e2b42` · 파랑 `#27508f`**).
