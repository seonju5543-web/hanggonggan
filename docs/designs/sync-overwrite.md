# 기기 사이 덮어쓰기 — 왜 칸을 쪼개는 것으로는 안 고쳐지는가 (2026-09-25)

> 기술 고문 보고서 **Q6** 이 지적한 사고다. 진단은 맞았고 **처방은 이 문제를 못 고친다.**
> 이 문서가 남는 이유는 하나다 — 다음 사람이 보고서만 읽고 `profiles` 표를 쪼개러 갈까 봐.

## 1. 실제로 무엇이 사라졌나

로그인은 2026-09-23 기준 **켜져 배포돼 있다**. 그 상태에서 이런 일이 난다.

```
폰 A: 신청서를 쓰고 올린다            → 서버 행 = {신청서 X}
폰 B: (A 를 모른 채) 프로필 한 칸 고침 → 저장 → 2초 뒤 push
      push 가 행을 **통째로** 갈아엎는다 → 서버 행 = {B 의 것뿐}
                                          **신청서 X 가 사라진다**
```

학생이 쓴 글은 다시 쓸 수 없다. 이것이 잃는 것 중 가장 비싼 쪽이다.

## 2. 원인은 모양이 아니라 '안 보는 것'이었다

- `app.js syncSchedulePush` 는 저장할 때마다 돌면서 **아무 확인 없이** `syncPush` 를 불렀다.
- `syncPush` 는 `Prefer: resolution=merge-duplicates` 로 **행 전체 upsert** 였다.
- 시각 비교(`theirs > mine`)는 `syncAfterLoad` 에만 있다 — **앱을 열 때 한 번뿐**이다.
  그 뒤의 모든 저장은 무조건 덮어썼다.

🔴 **칸을 쪼개도 그대로다.** 옛 기기는 쪼갠 칸들을 **제 옛 값으로 똑같이** 덮는다.
고쳐야 하는 것은 '내가 본 뒤로 서버가 움직였는가'를 **안 보는 것**이다.

⚠️ 그리고 `supabase/migrations/0001_profiles.sql` 은 칸을 안 쪼갠 이유를 이미 적어 뒀다 —
앱의 프로필 구조가 이미 두 번 바뀌었고(`migrateBranchCampus`·`migrateFitFields`),
칸으로 쪼개면 앱을 고칠 때마다 DB 도 같이 고쳐야 하며 **안 고치면 조용히 값이 사라진다.**
쪼개는 것이 공짜가 아니라는 뜻이다. (쪼개는 이득은 따로 있다 — 서버에서 자격을 재검증하거나
질의를 하려면 필요하다. 그건 **Q4 자동 발송**을 켤 때의 일이지 이 사고의 처방이 아니다.)

## 3. 지금 하는 일

**내가 마지막으로 본 판이 아직 서버에 있을 때만 고친다**(조건부 PATCH).

```
PATCH /rest/v1/profiles?user_id=eq.<나>&updated_at=eq.<내가 본 판>
  → 1행 돌아옴 = 내가 본 그대로였다. 고쳐졌다.
  → 0행 돌아옴 = 그 사이 다른 기기가 먼저 썼다.  **덮지 않는다.**
```

0행이면 `conflict` 로 알리고, 합치는 일은 **`app.js syncApplyRemote` 한 곳**이 맡는다
(합치는 규칙을 `supabase-client.js` 에 한 벌 더 두면 두 곳이 갈라진다).

🔴 **합칠 때 방향이 반대다.** `syncApplyRemote` 의 기본값은 '앱을 열었는데 서버가 더 새것'
이라 서버 프로필이 이긴다. 그런데 충돌은 **학생이 방금 이 기기에서 고쳐서** 올리려던
참에 난 것이다. 그대로 쓰면 방금 고친 값이 눈앞에서 되돌아간다(실측: 성적 4.1 → 3.6).
그래서 `{ quiet: true }` 가 있다 —

| | 기본 (앱 열 때) | `quiet` (덮어쓰기 충돌) |
|---|---|---|
| 프로필·동의 | 서버 것이 이긴다 | **이 기기 것을 둔다** (방금 고친 것) |
| 신청내역 | 합친다 | 합친다 |
| 화면 | 다시 그린다 | **안 그린다** (글을 쓰는 중일 수 있다 — 포커스가 날아간다) |

기준은 원래 있던 주석과 같다: **글은 다시 못 쓰고, 프로필 한 칸은 다시 고치면 된다.**

## 4. 되돌리면 깨지는 것 (관문 `verify/verify-supabase.js` [9] 절)

가짜 서버가 **조건부 PATCH** 를 흉내 내고(`?updated_at=eq.` 가 안 맞으면 빈 배열),
검사가 '다른 기기가 먼저 쓴' 상황을 직접 만든 뒤 이 기기에서 저장을 시킨다.

red-green 양방향 확인:
- `supabase-client.js` 의 조건을 빼면 → **다른 기기 신청서가 사라진다** ✗
- `app.js` 의 `syncPushMerging` 을 `syncPush` 로 되돌리면 → **이 기기 수정이 사라진다** ✗

⚠️ **검사도 같이 옮겼다.** 프로필이 나가는 것을 재던 검사 넷이 `method === 'POST'` 만
보고 있었는데, 두 번째부터는 PATCH 라 **첫 POST 만 보고 그 뒤를 못 본다** —
주민번호·계좌 검사가 조용히 무력해지는 자리였다. 지금은 `lastProfileRow()` 가
방식과 무관하게 마지막 쓰기를 집는다(뜻은 그대로, 자리만 옮겼다).

## 5. 아직 증명하지 못한 것

🔴 **가짜 서버는 `updated_at` 을 글자로 비교하고, 진짜 Postgres 는 시각으로 비교한다.**
JS 가 보내는 `...Z`(밀리초)와 Postgres 의 `timestamptz`(마이크로초)가 같은 순간으로
읽히면 맞지만, **진짜 서버에서 한 번 눌러 보기 전에는 증명된 것이 아니다.**
켜 보고 확인할 것: 저장을 두 번 했을 때 두 번째도 서버에 반영되는가(1행이 돌아오는가).
안 맞으면 매 저장이 conflict 로 떨어져 **합치기-재시도가 늘 한 번씩 더 돈다**(데이터는
안 잃지만 요청이 두 배가 된다).

⚠️ 서버 행의 `updated_at` 이 비어 있으면 걸 조건이 없다. 그런 행은 막지 않고 그냥 올린다 —
안 그러면 **다시는 못 올리는 상태**가 된다(표의 기본값 때문에 거의 없지만 구멍은 막아 뒀다).

## 6. 그래서 칸은 쪼갰는가 — 쪼갰다, 다른 목적으로 (2026-09-26)

위 1~5절은 **덮어쓰기**에 대한 답이다. 보고서 Q6 에는 요구가 하나 더 있었다 —
*"핵심 정보를 개별 컬럼으로 분리하고, 검증은 클라이언트가 아닌 DB CHECK 혹은 서버에서."*
그건 `supabase/migrations/0004_profile_columns.sql` 로 했다.

🔴 **두 일을 섞지 말 것.** 쪼개기는 덮어쓰기를 고치지 않고(옛 기기가 쪼갠 칸을 제 옛 값으로
똑같이 덮는다), 조건부 수정은 값 검증을 하지 않는다. 각각 다른 겹이다.

쪼개는 방법은 **DB 가 jsonb 에서 꺼내 채우는 칸**(`generated always as … stored`)이다 —
앱이 두 곳에 쓰게 하면 이 문서 2절이 설명한 것과 **같은 종류의 사고**가 한 겹 더 생긴다.
자세한 이유·CHECK 가 잡는 것과 못 잡는 것은 `docs/designs/data-model.md` 2절.

⚠️ **거절은 조용하면 안 된다** — 여기서 배운 것과 같은 교훈이다. 올리기 실패는
`app.js syncSchedulePush` 의 `.catch(() => {})` 에 통째로 삼켜지고 있었으므로,
DB 가 값을 보고 거절한 것만 따로 가려(`syncRejectText`) 화면이 **한 번** 알린다.
조건부 PATCH 라 알리지 않으면 **다음 저장도 같은 자리에서 막힌 채 영영 조용하다.**
관문 `verify/verify-supabase.js` [13] 절.
